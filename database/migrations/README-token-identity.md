# Token identity migration (issue #56)

`20261109-token-identity.sql` is an explicit MySQL 8 operator migration, never an application-startup migration. Follow [the runbook](../../docs/operations/token-session-identity-20261109.md). Stop token writers, take a private verified backup, and rehearse in an isolated restored schema before applying it. Execute in batch mode against an explicitly selected schema, **without `--force`**. Do not bypass failed guards with manual ALTER statements.

The accepted source is the audited `VARCHAR(255) utf8mb4_0900_ai_ci NOT NULL` column with no default/extra attributes, or the exact target `VARCHAR(2560) CHARACTER SET ascii COLLATE ascii_bin NOT NULL`. The table must be MySQL 8 InnoDB DYNAMIC with a page size of at least 16KiB. No foreign key may involve the token value itself. Incompatible column/table/index definitions, non-ASCII data, trailing spaces, oversized values and byte-identical duplicates (including revoked/expired sessions) abort before ALTER. No token values are printed by the script.

The target stores the complete token and has a full, visible, single-column BTREE unique index. An existing equivalent unique index is reused regardless of name; an unknown/incompatible `uk_token_value` or any incompatible index containing `token` aborts. Column-only and index-only partial target states are supported; a fully applied migration skips. Dirty-data guards still run on every execution. Column conversion and index creation, when both needed, use one atomic MySQL 8 InnoDB ALTER. DDL implicitly commits, may rebuild the table and requires a maintenance window; timeouts bound lock waiting, not execution duration.

2560 ASCII bytes stay below the 3072-byte InnoDB index limit under the guarded conditions. The identity source is `user.email VARCHAR(255)`, without a DTO character validator. The JWT writer emits supplementary Unicode directly as UTF-8 instead of two JSON surrogate escapes; control characters may still require six JSON bytes each. This leaves capacity for the current subject, timestamps, UUID jti and HS256 envelope. Arbitrarily large caller-supplied extra claims are not bounded by the schema; the current persisted login path supplies none. Tests cover all three paths without extra payload and the maximum identity, plus preservation/override protection for extra claims.

No rows are deleted, token IDs/timestamps changed, sessions revoked, signing keys changed, or jti column added. Historical signed JWTs without jti remain valid subject to their original expiry and session state. `database/system.sql` mirrors the new empty-schema definition only: it drops tables and **must never be imported into an existing database**. A rollback must retain the widened column/index while new tokens exist; do not narrow or remove constraints as an application rollback.

Local H2 tests exercise the snapshot's capacity/index and real mapper statements. H2 omits the MySQL character-set/collation clause; these tests are not a MySQL migration rehearsal or proof of live acceptance.
